# ModelGate Agent Studio：P0–P2 后续真实环境验收与生产化开发计划

> 制定日期：2026-07-18  
> 文档性质：P0–P2 完成后的下一阶段统一开发、验收与发布基线  
> 建议仓库路径：`docs/roadmap/2026-07-18-P0-P2后续真实环境验收与生产化开发计划.md`  
> 当前基线：P0–P2 核心代码已进入 GitHub；本地自动化测试已声明通过，但 GitHub CI、真实 Provider、正式数据库迁移、浏览器 E2E、真实并行与生产级安全性能门禁尚未完成。

---

## 1. 阶段判断

P0–P2 已经完成 Agent Runtime 的主要控制骨架：

- 结构化、版本化 `ExecutionPlan`。
- PlanTask、PlanChange 与 Runtime Task 来源追踪。
- DAG Scheduler、依赖调度、并发上限与阻塞状态。
- Retry、Handoff、Revise、Replan 的语义区分。
- Tool Call、Artifact、VerificationResult 与 Completion Gate。
- Shared RAG 的 Source、Document、Chunk、RetrievalRun、Citation 和 Context Budget。
- Capability Registry、Agent/Model Selector 与按需 Multi-Agent。
- Card Flow、Pixel Office、Plan、Context、Selection、Verification 等可视化状态。

下一阶段不应继续优先增加 Agent 角色、页面或概念，而应完成：

> **从“代码结构完成”到“真实环境稳定可复现”的跨越。**

本阶段统一目标：

```text
GitHub 可复现
+
真实 Provider 可运行
+
真实 Workspace 可修改
+
真实并行可合并
+
数据库可升级
+
浏览器可验收
+
安全与故障可控制
+
指标可证明
+
形成 Release Candidate
```

---

## 2. 本阶段总体目标

### 2.1 产品目标

1. 用户创建 Goal 后，真实模型可以完成规划、执行、验证、返工和交接。
2. Workspace 展示的 Agent、Task、并行、Handoff、Replan 和完成状态全部来自真实 Runtime。
3. 代码任务必须产生真实文件变更、命令结果、Artifact 和 Verification Evidence。
4. Multi-Agent 只有在真实收益高于协调成本时启用。
5. RAG 能在真实项目中检索正确资料，并可解释来源。
6. 任何失败都能形成明确状态，不能伪装为完成。

### 2.2 工程目标

1. 所有 Pull Request 自动执行后端、前端、构建和迁移检查。
2. 新库初始化与旧库升级均可重复执行。
3. direct、single、sequential、parallel 四类任务均有真实 E2E。
4. Provider 超时、429、错误 JSON、工具失败、合并冲突和进程重启均有恢复测试。
5. 发布前形成版本化 Release Candidate 和完整验收报告。

### 2.3 本阶段非目标

- 不建设无限自由拖拽工作流。
- 不增加大量固定 Agent 角色。
- 不开发 Skill Marketplace。
- 不接入大量 Vector Store。
- 不扩大企业权限与多人协作。
- 不在稳定性未验证前开发复杂像素动画。
- 不把 Mock 测试结果包装为真实模型成功率。
- 不为了展示效果强制启用 Multi-Agent。

---

## 3. 开发阶段划分

本计划划分为 P3–P7：

| 阶段 | 名称 | 核心结果 |
|---|---|---|
| P3 | GitHub CI 与可复现工程门禁 | 每次提交都可自动验证 |
| P4 | 真实 Provider 与 Agent Runtime E2E | 真实模型完成四种执行模式 |
| P5 | 正式数据库迁移与状态可靠性 | 新库、旧库、重启和恢复可靠 |
| P6 | 浏览器 E2E、真实并行 Worktree 与 RAG 质量 | 前端、Worktree、检索形成真实闭环 |
| P7 | 安全、性能、故障注入与发布候选 | 达到可发布 RC 标准 |

实施依赖：

```text
P3 CI
  ↓
P4 真实 Provider
  ↓
P5 正式迁移与恢复
  ↓
P6 浏览器 / Worktree / RAG
  ↓
P7 安全 / 性能 / Release Candidate
```

P3 和 P5 的部分任务可以并行；P4 的真实场景必须尽早开始，避免系统继续围绕 Mock 优化。

# 4. P3：GitHub CI 与可复现工程门禁

## 4.1 P3 目标

让 Review 中的“后端测试、前端测试、生产构建通过”从本地声明变成 GitHub 上可见、可重复、可阻止错误合并的自动门禁。

## 4.2 P3-1：建立 GitHub Actions

新增：

```text
.github/workflows/backend-ci.yml
.github/workflows/frontend-ci.yml
.github/workflows/integration-ci.yml
.github/workflows/security-ci.yml
```

### Backend CI

执行：

1. 安装指定 Python 版本。
2. 安装锁定依赖。
3. 静态导入检查。
4. Ruff 或 Flake8。
5. MyPy 或 Pyright，至少覆盖核心 Service 与 Schema。
6. Pytest。
7. Coverage 报告。
8. 数据库空库初始化。
9. Migration smoke test。

建议命令：

```bash
pytest -q
pytest --cov=src --cov-report=term-missing --cov-report=xml
ruff check .
mypy src/services src/schemas
```

### Frontend CI

执行：

1. 安装指定 Node.js 版本。
2. 使用 lockfile 安装依赖。
3. ESLint。
4. TypeScript typecheck。
5. Vitest。
6. Production build。
7. 上传测试和构建报告。

建议命令：

```bash
npm ci
npm run lint
npm run typecheck
npm run test -- --run
npm run build
```

### Integration CI

执行：

1. 启动测试数据库。
2. 启动 Backend。
3. 启动 Frontend。
4. 执行 API smoke test。
5. 执行最小 Playwright E2E。
6. 保存日志和失败截图。

## 4.3 P3-2：锁定运行环境

必须固定：

- Python 版本。
- Node.js 版本。
- npm/pnpm 版本。
- SQLite 版本或 PostgreSQL 镜像版本。
- Docker Compose 版本。
- Playwright 浏览器版本。

新增或确认：

```text
.python-version
.nvmrc
package-lock.json / pnpm-lock.yaml
requirements.lock / uv.lock / poetry.lock
```

禁止 CI 中使用无版本上限的核心依赖。

## 4.4 P3-3：分支保护

为 `main` 开启：

- 禁止直接推送。
- 必须通过 Pull Request。
- 必须通过 Backend CI。
- 必须通过 Frontend CI。
- 必须通过 Integration CI。
- 必须保持分支最新。
- 至少一名 Reviewer 或自审检查单。
- 禁止未解决 Conversation 合并。

## 4.5 P3-4：测试分层

统一测试分类：

```text
unit
integration
e2e
provider
slow
security
```

Pytest Marker 示例：

```python
@pytest.mark.unit
@pytest.mark.integration
@pytest.mark.provider
@pytest.mark.slow
```

默认 PR 执行：

- unit
- integration
- 最小 e2e

Nightly 执行：

- provider
- slow
- security
- 完整浏览器矩阵

## 4.6 P3-5：覆盖率与质量阈值

初始建议：

- 后端总覆盖率不低于 75%。
- 核心 Runtime Service 不低于 85%。
- Planning、Verifier、Replan、Selector 不低于 90%。
- 前端核心 ViewModel、Plan、Task、Context、Final Output 不低于 80%。

Coverage 不是最终质量指标，但用于防止核心路径无测试回归。

## 4.7 P3 验收标准

- [ ] PR 自动运行所有基础工作流。
- [ ] 任一测试失败会阻止合并。
- [ ] GitHub Commit 显示明确 Checks。
- [ ] 后端、前端、构建结果可下载。
- [x] 新开发者仅按 README 即可复现测试。
- [ ] `main` 开启分支保护。
- [ ] P0–P2 全量测试在 CI 中通过。

# 5. P4：真实 Provider 与 Agent Runtime E2E

## 5.1 P4 目标

证明 Agent Studio 不只是能通过 Mock 生成状态，而是可以使用至少一个真实 OpenAI-compatible Provider 完成真实 Goal。

## 5.2 P4-1：统一 Provider 配置

环境变量建议：

```env
MODEL_GATE_EXECUTION_MODE=real
PROVIDER_API_BASE=
PROVIDER_API_KEY=
PLANNER_MODEL_NAME=
WORKER_MODEL_NAME=
VERIFIER_MODEL_NAME=
EMBEDDING_MODEL_NAME=
```

要求：

- API Key 不写入数据库日志和前端。
- Provider 配置支持环境变量覆盖。
- 数据库保存模型标识，不保存明文密钥，或只保存加密密钥。
- `ModelRequest.model` 必须传真实 Provider 模型名，不得误传数据库 UUID。
- 健康检查与生成请求使用同一个模型标识策略。
- Provider 错误映射为统一错误类型。

统一错误类型：

```text
provider_auth_error
provider_rate_limited
provider_timeout
provider_context_overflow
provider_invalid_response
provider_unavailable
provider_tool_call_error
```

## 5.3 P4-2：真实规划 E2E

测试真实 Planner：

1. 输入简单解释任务。
2. 输入单文件修改任务。
3. 输入 Bug + Test 任务。
4. 输入研究后编码任务。
5. 输入前后端并行任务。
6. 输入高风险数据库迁移任务。

校验：

- 输出符合 `ExecutionPlanContract`。
- Task ID 唯一。
- DAG 无环。
- 写任务存在 Completion Contract。
- 高风险任务包含审批或独立验证。
- 并行任务 Scope 不冲突。
- 修复重试可工作。
- 无效三次后明确进入 Rule Fallback。

记录指标：

- 首次 Plan Validity Rate。
- 平均修复次数。
- Rule Fallback Rate。
- 规划 Token。
- 规划延迟。
- 规划成本。

## 5.4 P4-3：真实 Worker Tool Loop

至少支持真实执行：

- 文件读取。
- 文件创建。
- 文件修改。
- Git diff。
- 测试命令。
- Lint。
- Typecheck。
- Build。
- Artifact 注册。

统一循环：

```text
Observe
→ Decide
→ Tool Call
→ Tool Result
→ Update Context
→ Continue / Verify / Fail
```

必须限制：

- 最大步骤数。
- 最大 Token。
- 最大持续时间。
- 最大连续失败。
- 工具白名单。
- Workspace Scope。
- 命令超时。
- 输出长度。

## 5.5 P4-4：六类真实 E2E Goal

### 场景 A：direct

输入：

```text
解释指定文件中的一个函数。
```

预期：

- 不创建多余 Planner/Reviewer Worker。
- 只读文件。
- 返回带文件来源的解释。
- 不产生无意义 Artifact。

### 场景 B：single_agent

输入：

```text
修改 README 中的一句话。
```

预期：

- 一个 Coder。
- 真实生成 Git diff。
- `diff_exists` 通过。
- Goal 进入 completed。

### 场景 C：Coder → Verifier

输入：

```text
修复一个可复现 Bug 并运行测试。
```

预期：

- Coder 修改文件。
- 测试失败时 Revise。
- 测试成功后 completed_verified。
- 无测试证据不能完成。

### 场景 D：Research → Coder → Verifier

输入：

```text
先阅读架构文档，再修改代码并验证。
```

预期：

- Research 结果进入 Coder Context。
- Coder 不重新全量读取无关内容。
- Verifier 引用验收规则与真实命令证据。

### 场景 E：Parallel Multi-Agent

输入：

```text
前端和后端分别实现独立功能并安全合并。
```

预期：

- 两个独立 Worktree。
- 两个 Worker 真实并发。
- Merge Task 真实执行。
- 冲突时进入 Resolution Task。
- 成功后统一 Verifier。

### 场景 F：Replan / Handoff

输入可制造：

- Provider 429。
- Agent 工具权限不足。
- 原计划假设错误。
- 验证发现架构问题。

预期：

- 429 或额度问题触发 Handoff。
- 能力错误触发换 Agent。
- 目标不变、输出不合格触发 Revise。
- Plan 错误创建新版本 Replan。

## 5.6 P4-5：流式状态

真实运行时前端应收到：

```text
plan.generating
plan.created
plan.confirmed
task.ready
task.assigned
worker.started
model.streaming
tool.started
tool.completed
artifact.created
verification.started
verification.passed
task.completed_verified
goal.completed
```

要求：

- 刷新页面后状态可恢复。
- 断线重连不重复执行 Task。
- UI 不通过本地定时器伪造进度。
- Streaming 中断后进入可恢复状态。

## 5.7 P4 验收标准

- [ ] 至少一个真实 Provider 跑通六类场景。
- [ ] Planner 真实输出 Plan Contract。
- [ ] Worker 真实调用文件和命令工具。
- [ ] Verification 使用真实 ToolCallRecord。
- [x] Provider 错误可分类并恢复。
- [x] Rule Fallback 原因在 Workspace 可见。
- [ ] 真实运行日志中无 API Key。
- [ ] 形成真实 E2E 验收报告。

# 6. P5：正式数据库迁移与状态可靠性

## 6.1 P5 目标

替代当前 SQL 文件 + SQLite additive helper 的临时迁移方式，建立正式版本治理。

## 6.2 P5-1：引入 Alembic

建立：

```text
backend/alembic.ini
backend/alembic/
backend/alembic/versions/
```

将现有迁移纳入版本链：

- 初始 Schema。
- Runtime V2。
- ExecutionPlan。
- Scheduler Policy。
- Knowledge/Retrieval。
- Capability Registry。

每个迁移必须包含：

- revision。
- down_revision。
- upgrade。
- downgrade 或明确前向修复策略。
- 索引和唯一约束。
- 数据默认值与兼容处理。

## 6.3 P5-2：三类迁移测试

### 空库初始化

```text
empty database
→ alembic upgrade head
→ create seed data
→ API smoke test
```

### 旧库升级

```text
schema version 012
→ upgrade to head
→ preserve Goals / Tasks / Agents / Handoffs
→ verify new columns and constraints
```

### 重复执行

```text
alembic upgrade head
→ repeat
→ no duplicate column/table/index
```

## 6.4 P5-3：SQLite 与 PostgreSQL

建议：

- 本地开发保留 SQLite。
- CI 和生产验收加入 PostgreSQL。
- ORM 查询必须同时通过两种数据库。
- SQLite helper 仅用于极旧本地库兼容，逐步废弃。
- 不依赖 SQLite 特有隐式行为。

重点检查：

- Boolean。
- DateTime timezone。
- JSON/Text 序列化。
- 并发写。
- 唯一约束。
- Foreign Key。
- Transaction rollback。

## 6.5 P5-4：Runtime 状态一致性

建立状态机约束。

### Goal 状态

```text
draft
planning
waiting_confirmation
running
paused
waiting_approval
revision_required
blocked
completed
failed
cancelled
```

### Task 状态

```text
pending
ready
assigned
running
waiting_approval
completed_verified
completed_unverified
revision_required
blocked
skipped
cancelled
failed
```

要求：

- 非法状态跳转被拒绝。
- 状态更新与事件写入同一事务。
- Task 完成与 Artifact、Verification 同一事务或可恢复事务。
- Replan 激活新版本与旧版本 superseded 原子完成。
- Handoff 接受与 Worker 责任转移原子完成。

## 6.6 P5-5：进程重启恢复

模拟：

1. Worker 执行中进程退出。
2. Tool 完成但 Task 状态未更新。
3. Plan 激活一半时退出。
4. Merge 进行中退出。
5. Provider Streaming 中断。
6. 数据库连接短暂中断。

恢复规则：

- `running` Task 超过租约时间进入 recoverable。
- 幂等 Tool 不重复执行或使用 idempotency key。
- 非幂等 Tool 要求人工确认。
- Scheduler 重启后只读取 Active Plan。
- 已验证 Task 不重复执行。
- Artifact checksum 用于避免重复注册。

## 6.7 P5 验收标准

- [x] Alembic 管理全部迁移。
- [x] 空库初始化通过。
- [x] 旧库升级通过。
- [x] PostgreSQL 集成测试通过。
- [x] 非法状态跳转被阻止。
- [x] 关键状态更新具有事务性。
- [x] 进程重启后 Goal 可恢复。
- [x] 已验证 Task 不重复执行。

# 7. P6：浏览器 E2E、真实并行 Worktree 与 RAG 质量

## 7.1 P6 目标

把组件测试覆盖扩展到真实浏览器、真实文件系统和真实项目知识库。

## 7.2 P6-A：Playwright 浏览器 E2E

### 测试页面

- Studio。
- Goal 创建。
- Plan Overview。
- Card Flow。
- Pixel Office。
- Task Detail。
- Context Tab。
- Handoff。
- Evolution Review。
- Knowledge Sources。
- Final Output。

### 核心场景

1. 创建 Goal。
2. 等待 Plan。
3. 确认 Plan。
4. 查看 Task 分支。
5. 切换 Card / Pixel。
6. 打开 Agent Detail。
7. 查看 Tool、Artifact、Verification。
8. 触发 Handoff。
9. 触发 Replan。
10. 刷新页面恢复状态。
11. 查看最终输出。
12. 禁用错误 Knowledge Source 后 Retry。

### 视觉和布局

至少覆盖：

- 1280×720。
- 1440×900。
- 1920×1080。
- 小屏宽度。
- 长 Plan。
- 20+ Task DAG。
- 多次 Replan。
- 长 Context Chunk。
- 大量 Selection Candidates。
- Pixel/Card 连续切换。

### 必查问题

- 文本溢出。
- 固定定位遮挡。
- Pixel Office 重复渲染文字。
- Task 连线错位。
- Modal 超出视口。
- 切换视图后选中 Task 丢失。
- 页面刷新后 Plan/Task 不一致。
- 前端状态与 API 状态不一致。

## 7.3 P6-B：真实 Worktree 与并行执行

### Worktree 生命周期

```text
create
→ assign
→ execute
→ diff
→ verify
→ merge
→ cleanup
```

需要记录：

- Worktree ID。
- Branch。
- Workspace Path。
- Task ID。
- Agent ID。
- 创建时间。
- 合并状态。
- 清理状态。

### 并行安全

调度前检查：

- Workspace Scope。
- 文件交集。
- Agent 并发容量。
- 工具资源。
- 端口冲突。
- 数据库写冲突。
- Build cache 冲突。

### Merge

要求：

- 合并顺序确定。
- 保存每个分支 Commit SHA。
- 合并前各分支独立验证。
- 合并后执行统一测试。
- 冲突保存文件列表和 Git 输出。
- 冲突进入 Resolution Task。
- Resolution Task 完成后重新验证。

### 容量降级

当只有一个可用 Coder 或资源不足时：

```text
parallel_multi_agent
→ sequential_multi_agent
```

必须：

- 更新计划或记录运行政策降级。
- Workspace 显示真实串行状态。
- 不保留伪并行指标。

## 7.4 P6-C：RAG 质量评测

### 建立小型评测集

准备 30–50 个问题，覆盖：

- 项目架构。
- API。
- 数据模型。
- 启动方式。
- UI 规范。
- 历史 Bug。
- Skill。
- Handoff。
- 已禁用错误 Memory。
- 无答案问题。

每个问题标注：

- 正确 Source。
- 正确 Document。
- 正确 Chunk。
- 是否应返回空结果。
- 是否允许跨 Scope。

### 指标

- Recall@5。
- Precision@5。
- MRR。
- nDCG@5。
- Empty Result Accuracy。
- Forbidden Scope Retrieval Rate。
- Disabled Knowledge Retrieval Rate。
- Context Used Ratio。
- Retrieval Latency P50/P95。

### Embedding Adapter

实现：

```text
LocalHashEmbeddingAdapter
RealEmbeddingProviderAdapter
OptionalLocalEmbeddingModelAdapter
```

要求：

- Adapter 可配置。
- Embedding 维度写入元数据。
- 模型变更后支持重建索引。
- 不同版本 Embedding 不混算。
- Provider 不可用时可降级。
- 降级原因可见。

### 检索性能

当前全量 Chunk Python 遍历需要优化。

候选方案：

1. SQLite FTS5 + 向量 Adapter。
2. PostgreSQL `tsvector` + pgvector。
3. 先关键词召回 Top-N，再向量与 Rerank。
4. 批量加载 Embedding，避免逐行 JSON decode。
5. 为大型 Source 增加分页与异步同步。

# 8. P7：安全、性能、故障注入与发布候选

## 8.1 P7 目标

证明系统不仅能在理想路径工作，还能在高风险输入、异常 Provider、工具失败和并发压力下保持可控。

## 8.2 P7-A：安全门禁

### Workspace 路径安全

检查：

- `../` 路径穿越。
- Symlink 越界。
- 绝对路径。
- 大小写路径差异。
- macOS/Linux 路径兼容。
- Worktree 路径逃逸。
- Knowledge Source Scope 越权。

所有文件工具统一使用：

- `realpath`。
- `commonpath`。
- Workspace Root。
- Agent Scope。
- Tool Scope。

### Shell 安全

分类：

```text
safe_read
safe_build
workspace_write
network_access
destructive
privileged
```

规则：

- destructive 默认禁止。
- network_access 受政策控制。
- 命令有超时。
- 禁止 shell 拼接未转义用户输入。
- 禁止读取 `.env`、SSH Key、系统密钥目录。
- 输出脱敏。
- 命令记录可审计。

### Prompt Injection

RAG 文档和 Workspace 文件可能包含恶意指令。

需要：

- Context Item 标记为“不可信数据”。
- System Prompt 明确禁止执行文档内指令。
- Tool 权限不受检索内容改变。
- 外部文档不能提升权限。
- 高风险操作需要 Approval。
- Citation 不等于信任。

### Secret 管理

- API Key 不进入前端 Bundle。
- 不写入 ExecutionLog。
- 不写入 Handoff Summary。
- 不写入 Context Snapshot。
- 错误堆栈脱敏。
- `.env` 加入 `.gitignore`。
- CI 使用 GitHub Secrets。
