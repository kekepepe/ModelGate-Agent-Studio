# ModelGate Agent Studio 团队模板与 Dify 式易用性改造计划（P0–P2）

> 制定日期：2026-07-17  
> 文档性质：产品决策、分期开发计划与验收标准。  
> 关联基线：[下一阶段产品与开发总方案](2026-07-14-下一阶段产品与开发总方案.md)。如有冲突，以该文档中“Workspace 是主产品入口、Handoff 是 Task 内动作”的原则为准。

---

## 1. 为什么要改

当前 Agent Registry 的创建路径是“选 Agent 模板 → 三步表单 → 填模型、工具、Prompt、限制和 Handoff”。它适合运维底层 Agent 工位，但不适合普通用户快速完成一个实际任务。

用户真正想表达的是：

```text
我要完成哪类交付？
```

而不是：

```text
我要先配置哪个 Agent、哪个模型、哪些 Token 限制？
```

Dify 的可借鉴之处是用应用 / 模板卡片缩短创建路径；但 ModelGate 不应复制为纯工作流搭建器。Dify 的核心单位是“AI 应用或节点工作流”，ModelGate 的核心单位应是“可执行、可解释、可接管、可复盘的 Agent 团队”。

## 2. 产品定位与总原则

### 2.1 定位

> Dify 帮用户搭建 AI 应用；ModelGate 帮用户运营一支可解释、可接管、可复盘的 AI 团队。

### 2.2 三层信息架构

```text
Studio（默认入口）
  └─ 团队模板卡片：选择一类交付能力
       └─ Team Builder：配置可复用的团队
            └─ Workspace：执行一次具体 Goal，并观察、干预和复盘

Assets（高级配置层）
  └─ Agents / Models / Tools / Knowledge / Settings
```

| 层级 | 用户问题 | 主要对象 | 默认可见内容 |
|---|---|---|---|
| Studio | 我要完成什么？ | Team Template / Team | 团队模板卡片、最近运行、快速创建 |
| Team Builder | 这支团队如何完成它？ | Team、角色绑定、运行策略 | 团队流、成员配置、预算与测试 |
| Workspace | 这次任务进行得怎样？ | Goal、Task、Worker、Handoff | 状态、输出、路由理由、人工干预 |
| Assets | 系统有哪些可复用能力？ | Agent、Model、Tool、Knowledge | 高级资产管理与审计 |

### 2.3 必须遵守的设计原则

1. **卡片代表可交付的团队能力，不代表单个 Agent。**
2. **默认简单，高级渐进披露。** 首屏只显示模型、工具、职责；Prompt、备用模型、Token、超时和 Handoff 阈值进入高级设置。
3. **配置与运行分离，但关联可追溯。** Team 是可复用定义；每次 Goal 保存不可变的配置快照。
4. **Workspace 仍是运行主入口。** Handoff 不重新变成单独页面。
5. **不伪造画布能力。** 在 Runtime 支持条件分支、任意 DAG 与并行调度之前，Team Builder 只表达真实可执行的串行 / 简单依赖流。

## 3. 目标体验

### 3.1 Studio 卡片

```text
┌──────────────────────────────────────────────┐
│ 代码交付团队                                  │
│ 把需求拆解、编码、审查串成一次可追踪交付       │
│                                              │
│ Planner  →  Coder  →  Reviewer                │
│ 速度优先 · 可人工交接 · 3 个工具               │
│                                              │
│ [立即运行]              [配置]  [···]         │
└──────────────────────────────────────────────┘
```

首批固定模板：

| 模板 | 适用任务 | 默认角色流 |
|---|---|---|
| 代码交付团队 | 功能开发、修复、代码审查 | Planner → Coder → Reviewer |
| 深度调研团队 | 检索、分析、结论与风险 | Planner → Research → Summarizer → Reviewer |
| 文档生产团队 | 报告、方案、说明文档 | Planner → Research → Writer / Summarizer → Reviewer |
| 自定义团队 | 已有明确团队设计的高级用户 | 用户选择角色与顺序 |

### 3.2 Team Builder

```text
┌─────────────────────────────────────────────────────────────────┐
│ 团队名称 · 保存草稿 · 测试运行 · 发布版本                         │
├──────────────┬────────────────────────────┬─────────────────────┤
│ 目标与规则   │ 团队协作流                 │ 当前成员配置        │
│              │ [规划] → [执行] → [审查]  │ 模型               │
│ 输出类型     │ 点击节点切换配置对象       │ 工具               │
│ 完成标准     │                            │ 职责 / 指令         │
│ 预算策略     │                            │ [高级设置]         │
├──────────────┴────────────────────────────┴─────────────────────┤
│ 预计成本 · 风险提示 · 配置校验 · 最近一次测试结果                 │
└─────────────────────────────────────────────────────────────────┘
```

右侧成员配置的默认字段：

- 职责说明（自然语言）
- 默认模型
- 已启用工具（按类别展示并显示风险）
- 输出类型

仅在“高级设置”中显示：System Prompt、备用模型、最大步数、Token / 时长上限、连续失败阈值、自动 Handoff 规则。

### 3.3 Workspace

从“立即运行”进入 Workspace，用户填写 Goal、约束和完成标准后执行。Workspace 沿用现有的 Task、路由、风险、Handoff、日志和最终报告能力；同时显示“本次运行采用 Team X vY 的快照”，但不允许中途静默修改团队定义。

## 4. 分期计划

## P0：让首次配置像使用模板一样简单

### 目标

在不大改 Runtime 和数据库核心结构的前提下，让用户能从团队模板卡片进入 Workspace；将 Agent Registry 从日常起点降级为高级资产管理。

### 范围

#### 前端

1. 新增 `StudioPage`，作为 `/` 默认入口。
2. 将现有 Agent Templates 组合为首批团队模板卡片；配置可以暂时写在前端常量或后端模板数据中。
3. 每张卡片提供：`立即运行`、`配置`、`复制`。
4. `立即运行`：进入 Workspace，并预填 Goal 类型、推荐 Agent / 模型选择与运行约束。
5. `配置`：打开单页 Team Builder / 侧滑 Sheet，而不是复用三步 `AgentConfigForm`。
6. 将 Agent Registry 改名为 `Agents` 并移动到 Assets 语义下；保留原有 CRUD 和 URL 兼容性。
7. 调整顶层导航为：`Studio | Workspace | Assets | Evolution | Logs`；Assets 内再进入 Agents、Models、Tools。
8. 在 Agent 编辑页将字段分为“基础配置”和“高级设置”，默认折叠高级项。

#### 后端

1. 不改变现有 `AgentStation`、Runtime、Handoff 的行为。
2. 允许 Goal 创建接口接收可选的 `template_id` / `team_preset`，仅作为启动时选择默认 Agent 的提示信息。
3. 在 Goal / Workspace State 中返回本次启动所用的模板标识和展示名称。

### 非目标

- 不持久化可编辑 Team。
- 不做拖拽连线、任意 DAG、版本历史和导入导出。
- 不改变 Handoff 的 Task 内交互。

### 验收标准

1. 新用户可以在不进入 Agent Registry 的情况下，用不超过两次主要点击进入一个预配置 Workspace。
2. 四类团队模板均能生成可执行的默认 Agent 组合。
3. Agent Registry、Model Manager 和 Tool Manager 的现有操作不回归。
4. Workspace 能清晰显示本次运行使用的团队模板。
5. Handoff 仍只在 Task / Workspace 内完成。

### 建议实现顺序

1. 定义前端 `TeamPreset` 类型和四个模板。
2. 实现 Studio 卡片和路由。
3. 扩展 Goal 创建参数与 Workspace 展示字段。
4. 改造导航与 Agent 配置表单的渐进披露。
5. 补前端交互测试与后端契约测试。

## P1：让团队成为可复用、可版本化的产品对象

### 目标

将 P0 的静态团队模板升级为持久化 Team，使用户可以保存、复制、测试、发布、回滚团队配置，并保证每次运行可复现。

### 新数据模型

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `TeamTemplate` | id、name、description、category、default_definition | 系统或用户提供的起始模板 |
| `Team` | id、name、description、template_id、current_version_id、status | 用户可复用的团队 |
| `TeamVersion` | id、team_id、version、definition、created_by、created_at、status | 不可变配置版本，可发布 / 回滚 |
| `TeamAgentBinding` | team_version_id、position、agent_id / role、overrides | 一个团队版本中的成员与覆盖配置 |
| `GoalTeamSnapshot` | goal_id、team_version_id、resolved_definition | Goal 启动时冻结的完整配置 |

`resolved_definition` 至少包括：角色顺序、每个角色的 Agent / 模型 / 工具 / Prompt / 执行限制、默认 Handoff 规则、运行策略与 Team 版本号。

### 核心流程

```text
选模板 → 配置 Team 草稿 → 测试运行 → 发布 Team v1
                                ↓
                         修订并发布 v2
                                ↓
用某版本启动 Goal → 写入 GoalTeamSnapshot → Workspace 执行与复盘
```

### 范围

#### 前端

1. Studio 同时展示“系统模板”“我的团队”“最近运行”。
2. Team Builder 支持保存草稿、复制、测试运行、发布版本、查看版本差异和回滚。
3. 在每个成员节点旁显示模型、工具数量、风险和覆盖状态。
4. Workspace 显示 Team / 版本 / 快照入口；只读展示运行快照。
5. Agent Registry 中显示“被哪些 Team 版本引用”，避免误改公共 Agent 造成不可见影响。

#### 后端 / API

1. 新增 Team、Version、Binding、Snapshot 表及迁移。
2. `POST /teams`、`GET /teams`、`GET /teams/{id}`、`PATCH /teams/{id}`。
3. `POST /teams/{id}/versions`、`POST /teams/{id}/publish`、`POST /teams/{id}/rollback`。
4. `POST /goals` 接受 `team_version_id`，解析后写入不可变 `GoalTeamSnapshot`。
5. Runtime 只从 Goal Snapshot 获取该次运行配置；不读取后来变更的 Team / Agent 设置。
6. 增加依赖校验：模型可用、工具已启用、角色完整、风险工具有策略、引用对象未失效。

### 非目标

- 不开放任意图编辑。
- 不做多人权限审批；保留单用户本地模型。
- 不把 Agent、Model、Tool 的全局资产删除逻辑改成复杂级联。

### 验收标准

1. 用户可从模板创建 Team、保存草稿、测试、发布 v1，并复制为新 Team。
2. Team 发布后可以创建 v2，并回滚为 v1；历史版本不被覆盖。
3. 同一个 Team 的不同版本启动的两个 Goal，均可独立复现各自配置。
4. 运行中的 Goal 不受 Team / Agent 后续修改影响。
5. 不可用模型、缺失工具或不完整角色流会阻止发布，并说明具体原因。

## P2：在真实 Runtime 能力基础上开放可视化编排

### 目标

将 Team Builder 从线性协作流升级为有限、可验证的可视化编排，同时提升路由、预算与人工介入的可见性。

### 前提条件

以下能力必须已由 Runtime 和测试证明，再开放对应画布能力：

| 画布能力 | 必要 Runtime 能力 |
|---|---|
| 条件分支 | 任务条件、变量、可恢复状态与错误分支 |
| 并行节点 | 并行调度、依赖收敛、资源 / 额度隔离 |
| 循环或重试 | 终止条件、最大次数、幂等性和成本保护 |
| 自定义 Handoff 边 | 上下文快照、接手校验、审计时间线 |

### 范围

1. Team Builder 支持受限节点：角色节点、Review Gate、条件节点、人工确认点、Handoff 策略节点。
2. 画布只允许通过后端 `validate` 接口校验后保存；不能执行的图不允许发布。
3. 每个节点都能查看：输入、输出契约、模型策略、工具权限、预算、失败策略与可追溯日志。
4. 增加 Team 级别的运行指标：成功率、平均时长、Token / 估算成本、Handoff 率、人工干预率、质量审查结果。
5. 允许对 Team Version 做受控对比测试，但不自动把“表现较好”配置覆盖生产版本。

### 不做的事项

- 不做无限自由画布或“任何连线都允许”的低代码编辑器。
- 不做未经验证的自动自优化。
- 不将复杂编排的错误处理隐藏在视觉效果之后；每条边必须有可解释的执行语义。

### 验收标准

1. 用户可创建、校验并发布包含串行、人工确认与 Handoff 策略的 Team 图。
2. 若 Runtime 已支持并行 / 条件，则能在测试环境完成相应图的端到端运行并展示真实状态。
3. Workspace 能将运行中的 Task 对应回 Team 图节点，显示当前状态、模型、风险与下一步。
4. 每个已发布 Team Version 均可导出为不含密钥的可迁移定义；导入后经过版本与依赖校验。

## 5. 跨阶段技术与体验约束

### 5.1 配置快照不可省略

全局 Agent 可被多人 / 多个 Team 引用。若 Runtime 每次都读取当前 AgentStation，后续修改会让历史运行无法复现。因此 P1 起 Goal 必须持有完整运行快照；历史日志、成本和 Handoff 都关联此快照。

### 5.2 工具与密钥

Team 导入导出只能包含工具引用、权限策略和参数结构，不能包含 API Key 或其他 Secret。高风险工具必须在 Team 配置和 Workspace 运行时都保留显式审批 / 审计点。

### 5.3 运行时人类控制

不论 P0、P1 还是 P2，用户始终应能在 Workspace：暂停、重试、覆盖模型、修改下一步要求、触发 / 取消 Handoff、查看路由理由与最终报告。

### 5.4 成功指标

| 指标 | P0 目标 | P1 / P2 目标 |
|---|---|---|
| 从进入产品到启动 Goal 的主要操作数 | ≤ 2 次 | ≤ 2 次 |
| 使用模板而非手工创建底层 Agent 的 Goal 占比 | 可观测 | 持续提升 |
| 可复现运行占比 | 标识模板 | 100% 有 Goal Snapshot |
| 配置发布失败的可解释性 | 明确提示 | 有字段级 / 图级校验原因 |
| 运行中人工介入可追溯性 | Workspace 可见 | Team / Version / Node 级可追溯 |

## 6. 推荐实施决策

先做 P0，不先做画布。

P0 直接改善当前最大的体验问题，且能复用现有 Agent Templates、Workspace、Runtime 与 Handoff；P1 再解决“团队可复用”和“运行可复现”的产品基础；P2 只在 Runtime 能力成熟后开放相匹配的图编辑。这样既能获得 Dify 式的低门槛入口，也不会牺牲 ModelGate 的多 Agent 执行与治理差异化。
