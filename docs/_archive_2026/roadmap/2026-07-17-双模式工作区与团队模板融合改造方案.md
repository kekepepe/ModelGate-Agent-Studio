## 1. 不可妥协的产品决定

### 1.1 双模式 Workspace 必须保留

`Card Flow View` 与 `Pixel Office View` 是同一 Workspace 的两种表达，不是可有可无的装饰功能，也不是两个页面。

```text
一份 WorkspaceState
  ├─ Card Flow Renderer：效率、任务流、状态判断、快速操作
  └─ Pixel Office Renderer：工位、Worker、模型、交接、产品识别
```

用户可在顶部一键切换。切换后必须保留：当前 Goal、Task、选中对象、Agent / Worker、模型绑定、Handoff、日志、额度、运行状态和动画语义。

### 1.2 工位并排展示是“协作认知模型”，不是对并行 Runtime 的虚假承诺

即使当前 Runtime 的执行计划主要是串行，Agent 工位也应该并排出现。它表达的是“这支团队有哪些岗位、当前谁待命、谁工作、任务下一步会去哪里”，而不是声称所有工位都在同时运行。

真实性规则：

- `running`：该工位当前真实有 Worker 在执行。
- `waiting / queued`：该工位已在协作链中，但等待依赖完成。
- `idle`：团队中存在该工位，但本次 Goal 尚未使用。
- `handoff`：显示任务由哪个工位、哪个模型交给哪个工位、哪个模型。
- 只有 Runtime 支持并行后，才同时显示多个真实 `running` 工位。

因此，前端从“纵向任务时间线”恢复为“并排 Agent 工位 + 有语义的任务连线”，不会误导用户，反而会让用户更清楚地理解协作状态。

### 1.3 详情交互恢复为两种模式

| Workspace 模式 | 详情承载方式 | 原则 |
|---|---|---|
| Card Flow View | `Agent Detail Modal` | 居中完整详情，包含 5 个 Tab，不固定挤占工作区 |
| Pixel Office View | `Station Popover` | 在所点工位附近显示轻量信息与快捷操作，可进入完整 Modal |

固定右侧 `TaskDetailPanel` 不再是默认详情交互。它可保留为窄屏适配或调试模式，但不能取代 Modal / Popover。

### 1.4 Dify 式卡片入口服务于“启动一支团队”，不替代双模式 Workspace

Studio 中的卡片是“团队能力模板”，用于快速开始；Workspace 中的卡片是“工位 / Agent Session”，用于理解执行。这两类卡片职责不同，不能混为一谈。

## 2. 融合后的产品结构

```text
Studio（默认入口）
  ├─ 团队模板卡片：代码交付 / 深度调研 / 文档生产 / 自定义团队
  ├─ 我的团队：已保存、版本化的 Team
  └─ 最近运行
       ↓ 立即运行 / 配置
Team Builder（可复用定义）
  ├─ 目标、完成标准、预算和运行策略
  ├─ 并排角色工位：Planner / Coder / Reviewer ...
  └─ 点击工位配置模型、工具、职责和高级策略
       ↓ 启动 Goal，冻结 Team Version Snapshot
Workspace（一次具体运行）
  ├─ Card Flow View：Agent 工位卡片与任务边
  ├─ Pixel Office View：像素工位、Worker 与交接文件夹
  ├─ Agent Detail Modal / Station Popover
  └─ Bottom Console：审计与运行摘要

Assets（高级管理）
  └─ Agents / Models / Tools / Knowledge / Settings
```

## 3. Workspace 最终布局

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Top Bar: Team v1 · Goal · Running · 2 Active · Quota · [Card] [Pixel]   │
│          [Pause] [Resume] [Stop] [Export Summary]                        │
├───────────────────┬─────────────────────────────────────────────────────┤
│ Left Control      │ Main Workspace Renderer                               │
│ Goal / Constraints│ Card Flow View  或  Pixel Office View                │
│ Run Config        │                                                     │
│ Task Tree         │ 点击对象：Modal / Popover，而非固定右侧栏             │
├───────────────────┴─────────────────────────────────────────────────────┤
│ Bottom Console（默认摘要；错误、Handoff 时自动展开）                      │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Top Bar

必须固定展示：

- Team 名称与版本快照；
- 当前 Goal、运行状态、活跃 Agent 数、Task 进度；
- 模型额度 / 风险摘要；
- `[Card Flow] [Pixel Office]` 模式切换；
- Pause、Resume、Stop、Export Summary。

### 3.2 左侧控制区

在两种模式下完全一致：

- Goal 输入与完成标准；
- Run Config：自动 Handoff、自动模型切换、工具审批、运行深度；
- Task Tree：点击后同步高亮 Card Flow 中对应工位 / 任务边，和 Pixel Office 中对应工位 / Worker。

### 3.3 Bottom Console

默认只显示一行摘要：

```text
Running · 12 Model Calls · 4 Tool Calls · 1 Handoff · 0 Errors
```

展开后包含：Event Log、Model Calls、Tool Calls、Token / Cost、Memory / Skill、Handoff Records、Errors。错误或 Handoff 发生时自动展开到相关事件。

## 4. Card Flow View：并排工位与任务流

### 4.1 核心表达

一个大卡片代表一个 `Agent Station`；当前 Worker、模型、任务卡和状态都在工位卡内。它不是普通的线性 To-do 列表。

```text
┌───────────────┐      ┌───────────────┐      ┌────────────────┐
│ Planner       │─────▶│ Coder         │─────▶│ Reviewer       │
│ Claude        │      │ DeepSeek      │      │ GPT            │
│ ● Done        │      │ ● Running     │      │ ○ Waiting      │
│ Task: 拆解需求│      │ Task: 实现页面│      │ Next: 质量审查 │
└───────────────┘      └───────────────┘      └────────────────┘
```

当 Team 有分支或 Runtime 已支持并行时，工位仍按角色位置排布，任务边表达真实依赖。例如 Research 与 Coder 可以同时为 Reviewer 提供输入；尚未支持并行时，两张卡都保留，但只显示实际运行的一张为 `running`。

### 4.2 Station Card 必须展示

- Agent 角色和名称；
- 当前模型（Worker 身份牌）；
- 状态灯、状态边框和状态文字；
- 当前 / 最近 Task；
- 最新输出摘要或下一动作；
- Token / 额度风险；
- 工具调用摘要；
- Handoff 标签与来源 / 目标；
- 点击打开 `Agent Detail Modal`。

已完成工位缩为 `Completed Stations` 区，但不会消失；被重新调用时恢复原工位卡或显示新的 Session 标记。

### 4.3 Task Edge 语义

| 连线 | 含义 | 视觉 |
|---|---|---|
| planned | 已规划、尚未执行 | 灰色虚线 |
| active | 当前真实推进路径 | 蓝色实线 / 低频流动效果 |
| done | 已完成依赖 | 绿色实线 |
| waiting | 等待依赖 / 人工确认 | 黄色虚线 |
| handoff | 上下文与任务转交 | 紫色线 + Handoff Summary 节点 |
| error | 失败或阻塞 | 红色线 + 原因标签 |

### 4.4 Card Flow 交互

- 点击工位卡：打开居中 `Agent Detail Modal`。
- 点击任务边：高亮上下游工位，并展示“为何等待 / 为何路由 / 为何交接”。
- 点击 Handoff Summary 节点：直接打开 Handoff Tab。
- 点击 Task Tree：同步高亮工位、Task 卡与相关边。
- 视图工具栏：Fit View、Show Completed、Edges On / Off、Auto Layout。

### 4.5 Agent Detail Modal

Modal 使用 5 个 Tab：

| Tab | 内容 |
|---|---|
| Overview | Agent、Worker、模型、状态、当前任务、Token、额度、最近输出 |
| Task | 任务输入、完成标准、进度、上下游依赖、结果 |
| Context | 已完成内容、约束、关键决定、加载的 Memory / Skill、传入上下文 |
| Tools | 已授权工具、调用记录、参数摘要、结果、风险与审批 |
| History | 模型调用、路由原因、失败、重试、Handoff 时间线 |

Modal 中提供：Pause Agent、Retry、Override Model、Generate / Accept Handoff、View Logs。操作是否可用由真实 Task 状态决定。

## 5. Pixel Office View：沉浸式协作观察模式

### 5.1 定位

Pixel Office 不是游戏，也不是另一个数据源。它是 Card Flow 的空间化呈现，用来回答：

```text
现在是谁在工作？
这个 Worker 用什么模型？
任务正在从哪个工位流到哪个工位？
为什么发生交接，谁在接手？
```

### 5.2 固定空间语义

| 场景元素 | 绑定对象 |
|---|---|
| 工位 / 桌牌 | Agent Station / 角色 |
| 像素 Worker | Worker Session 与当前模型 |
| 工位状态灯 | Agent / Task 真实状态 |
| 文件夹 / 任务纸张 | 当前 Task 或 Handoff Summary |
| Handoff Desk | 交接事件与待确认交接 |
| Supervisor Desk | 最终审查与质量结论 |
| Entrance | 新 Worker 加载 / 加入本次运行 |

### 5.3 Station Popover

点击工位时，在该工位附近打开不遮挡全局状态的轻量 Popover：

```text
Coder Station · DeepSeek Coder · Running
Task: 实现 Workspace
Latest: 正在写入组件
[View Full Detail] [Pause] [Handoff]
```

`View Full Detail` 打开与 Card Flow 完全相同的 `Agent Detail Modal`。这样两种模式的“完整信息”是一份内容，避免维护两套详情逻辑。

### 5.4 状态与动画纪律

- 动画只表达状态变化，不做持续炫技。
- Worker 入场：开始一个新的 Worker Session。
- 任务文件移动：Task 从上游变为下游可执行时。
- Handoff Folder：只在 Handoff Summary 已生成、接手方案可确认时出现；紫色路径连接来源与目标工位。
- 完成：Worker / 文件进入完成态，不删除历史痕迹。
- 错误：工位红色提示，Popover / Console 提供原因和下一步。

### 5.5 懒加载与降级

Pixel Office 使用独立懒加载 Chunk；首次切换显示 `Preparing Pixel Office…`。若像素资源加载失败，展示同一状态数据的简化 Station Grid，并允许返回 Card Flow，不能影响正在执行的 Goal。

## 6. Studio 与 Team Builder 的融合

### 6.1 Studio：Dify 式低门槛入口

首页使用团队模板卡片，而不是 Agent 配置表单：

```text
[代码交付团队]       [深度调研团队]
Planner → Coder      Planner → Research → Reviewer
[立即运行] [配置]    [立即运行] [配置]
```

点击 `立即运行`：预选 Team、进入 Goal 输入，随后启动双模式 Workspace。  
点击 `配置`：进入 Team Builder。

### 6.2 Team Builder：也使用工位并排表达

Team Builder 不做泛 Dify 节点画布。它使用与 Workspace 相同的 Agent Station 心智模型：并排工位代表角色、连线代表允许的任务流和 Handoff 方向；点击一个工位，在配置面板中编辑职责、模型、工具和高级策略。

```text
Planner Station  →  Coder Station  →  Reviewer Station
   [配置]              [配置]              [配置]
```

团队定义与运行展示相互呼应：用户在 Builder 中配置的工位，会在 Workspace 的 Card Flow 和 Pixel Office 中以同样的角色和位置出现。

## 7. 统一数据与前端架构

### 7.1 单一状态源

扩展现有 Workspace 聚合状态，建立前端 `WorkspaceViewModel`：

```ts
type WorkspaceViewModel = {
  goal: Goal;
  teamSnapshot: GoalTeamSnapshot;
  stations: StationViewModel[];
  tasks: TaskViewModel[];
  workers: WorkerViewModel[];
  edges: TaskEdgeViewModel[];
  handoffs: HandoffViewModel[];
  logs: LogViewModel[];
  quota: QuotaViewModel[];
  selection: { taskId?: string; stationId?: string; handoffId?: string };
};
```

### 7.2 两个 Renderer

| 模块 | 消费数据 | 只负责 |
|---|---|---|
| `CardFlowRenderer` | stations、tasks、edges、handoffs、selection | 卡片、连线、高亮、Modal 入口 |
| `PixelOfficeRenderer` | stations、workers、tasks、handoffs、selection | 工位、Worker、文件夹、Popover、动画 |
| `AgentDetailModal` | 选中 Station / Task / Handoff | 统一完整详情 |
| `BottomConsole` | logs、handoffs、quota | 审计与异常事件 |

任何状态更新必须先写入 ViewModel，再由两个 Renderer 同步渲染；禁止 Card Flow 和 Pixel Office 分别维护独立的 Task / Handoff 状态。

### 7.3 当前组件的改造映射

| 当前实现 | 改造后 |
|---|---|
| `TaskFlow` 纵向步骤列表 | `CardFlowRenderer` 的工位卡与任务边；保留其串行顺序信息作为边语义 |
| `TaskCard` | 嵌入 `AgentStationCard`，或作为工位内当前 Task 卡 |
| 固定 `TaskDetailPanel` | 默认替换为 `AgentDetailModal`；仅窄屏 / 调试保留 Drawer |
| `AgentStationCard` | 作为 Card Flow 的核心 Station Card，补齐模型、Worker、Task、Handoff、额度状态 |
| `HandoffConfirmModal` / `HandoffDetailDrawer` | 由 Agent Detail Modal 的 Handoff Tab 触发和承载；确认 Sheet 可保留 |
| `BottomConsole` | 保留并补齐摘要、Memory / Skill 和 Handoff 自动聚焦 |

## 8. 分期实施计划

## P0：恢复产品主视觉与双模式骨架

### 目标

在不改写 Runtime 核心执行模型的前提下，恢复并交付可用的 Card Flow + Pixel Office 双模式 Workspace，同时加入团队模板卡片入口。

### 前端范围

1. 新增 `StudioPage` 与四个 Team Preset 卡片。
2. 调整导航：`Studio | Workspace | Assets | Evolution | Logs`；Agent Registry 归入 Assets。
3. 将 `WorkspacePage` 固化为“Top Bar + 左侧控制 + 双模式主视图 + Bottom Console”，移除默认固定右侧详情栏。
4. 新增 `WorkspaceModeSwitch`、`CardFlowRenderer`、`PixelOfficeRenderer`、`StationPopover`、`AgentDetailModal`、`TaskEdge`。
5. 将当前 Task / Agent / Worker / Handoff 数据映射为 `WorkspaceViewModel`。
6. Card Flow 实现并排 Station Card、真实状态边、Completed Stations、Modal 五 Tab。
7. Pixel Office 实现静态办公室、固定工位、Worker 身份牌、状态灯、Station Popover、基础 Handoff Folder 路径。
8. 实现两种视图的选中、高亮、状态与 Handoff 同步；Pixel Office 按路由 / 切换懒加载。

### 后端范围

1. 在 Workspace State 中补齐 `task_edges` / 依赖、Station 与 Worker 的稳定映射、当前模型、quota、handoff 摘要。
2. Goal 创建临时接受 `team_preset`，并回传本次使用的模板信息。
3. 保持 Handoff 是 Task 内操作；不恢复日常独立 Handoff 页面。

### P0 验收标准

1. 用户能从 Studio 模板卡片，用不超过两次主要点击进入预配置 Workspace。
2. Workspace 默认显示并排 Card Flow 工位；每个工位能明确显示角色、模型、状态和当前 / 下一任务。
3. 点击 Card Flow 工位打开完整 Modal；点击 Pixel Office 工位打开 Popover 并可进入同一 Modal。
4. 模式切换不丢失选中 Task、运行状态、Worker、Handoff 或日志上下文。
5. Handoff 在两种模式下都能看出来源、目标、原因、摘要与接手状态。
6. 不支持并行时，UI 仍可并排展示工位，但只标记真实运行的 Worker 为 `running`。
7. Pixel Office 资源失败时不阻断 Goal 执行，可安全返回 Card Flow。

## P1：Team 版本化与运行快照

### 目标

将 P0 的静态 Team Preset 变为可保存、复制、测试、发布、回滚的 Team，并让 Builder、Card Flow 与 Pixel Office 使用同一份 Team 角色定义。

### 范围

1. 增加 `TeamTemplate`、`Team`、`TeamVersion`、`TeamAgentBinding`、`GoalTeamSnapshot` 数据模型与迁移。
2. Team Builder 以并排工位配置团队；点击工位编辑模型、工具、职责、Prompt 与 Handoff 策略。
3. 支持草稿、测试运行、发布、复制、版本差异、回滚和依赖校验。
4. Goal 从 `TeamVersion` 创建时写入不可变 Snapshot；Runtime 只读取 Snapshot。
5. Workspace Top Bar、Card Flow 和 Pixel Office 均显示 Team 名称与版本，并从 Snapshot 确定工位布局。

### P1 验收标准

1. 同一 Team 的 v1、v2 分别启动 Goal 后，两个运行均能重现各自的模型、工具、Prompt、工位与策略。
2. 后续修改全局 Agent 或 Team，不改变运行中的 Goal 或历史回放。
3. Team Builder 中配置的工位顺序和 Handoff 边，在两种 Workspace 模式中一致呈现。
4. 无效模型、缺失工具、不完整角色或不可执行边会阻止发布，并展示字段 / 连线级错误。

## P2：真实能力驱动的受限编排与观测增强

### 目标

在 Runtime 已验证支持条件、并行、循环和恢复后，扩展 Team Builder 的受限编排能力，并在两种 Workspace 模式中准确显示它们。

### 范围

1. Team Builder 增加条件边、Review Gate、人工确认点、受控并行组和 Handoff 策略节点。
2. 后端提供 Team 图校验；未通过 Runtime 语义校验的图不能发布。
3. Card Flow 支持真实分支 / 汇合与多个并发 `running` 工位。
4. Pixel Office 仅对已真实发生的并行、等待、交接和恢复显示对应空间状态与动画。
5. 增加 Team / Team Version 级指标：成功率、时长、Token / 成本、Handoff 率、人工干预率与审查质量。
6. 支持无 Secret 的 Team 定义导入 / 导出。

### P2 验收标准

1. 每一条 Team 边都有可执行、可验证且可追溯的 Runtime 语义。
2. Card Flow 与 Pixel Office 对分支、并行、Handoff、失败和恢复显示一致。
3. 用户可从任意运行中的工位追溯到 Team Version、配置快照、路由原因和执行日志。

## 9. 明确不做

- 不把 Pixel Office 降级为营销插画或静态背景。
- 不让 Pixel Office 承担关键配置或隐藏关键信息；其所有信息必须能在 Card Flow / Modal 中得到。
- 不做无法执行的自由节点画布。
- 不用“看起来并行”的动画掩盖串行或失败状态。
- 不把 Agent Registry 再次作为普通用户创建任务的起点。

## 10. 最终体验路径

```text
1. 用户进入 Studio，选择“代码交付团队”
2. 点击立即运行，填写 Goal 与完成标准
3. Workspace 默认进入 Card Flow
4. Planner、Coder、Reviewer 三个工位并排出现
5. 当前 Worker、模型、任务边和状态明确可见
6. 点击工位，在 Modal 中查看任务、上下文、工具和历史
7. 切换 Pixel Office，看到同一批工位、Worker 与任务文件
8. 发生 Handoff，紫色路径和文件夹从来源工位到接手工位
9. 点击接手工位，Popover 显示加载上下文与下一动作
10. Supervisor 完成审查，用户在两种模式和 Console 中看到最终结果与可追溯记录
```

## 11. 实施优先级结论

P0 的第一优先级不是更多管理页面，也不是自由流程画布，而是恢复 ModelGate 最有辨识度、也最能解释复杂协作的界面：**并排 Agent 工位、任务连线、双模式 Workspace、Modal / Popover 详情与可见 Handoff。**

团队模板卡片负责降低启动门槛；双模式 Workspace 负责让用户真正看懂和管理这支 AI 团队。二者共同构成 ModelGate 区别于 Dify 的前端核心。
