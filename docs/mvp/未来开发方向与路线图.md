# 未来开发方向与路线图

> 📌 **本文档收录所有 v0.1 MVP 暂不实现的功能，以及后续版本的规划方向。**
>
> 所有「很想要但 v0.1 不做」的功能，都记在这里。

---

## 一、v0.1 明确推迟的功能

### 1.1 核心能力层

| 功能 | 推迟原因 | 目标版本 | 优先级 |
|------|---------|----------|--------|
| 真实复杂自动代码修改 | 涉及文件系统、权限、回滚、diff，风险高 | v0.2 | P1 |
| 完整 MCP 插件生态 | 架构复杂，前期不需要验证 | v0.3 | P2 |
| 真实读取 Claude Code / Codex 额度 | API 不可控，技术难度高 | 长期 | P3 |
| 完整像素办公室动画 | 拖慢核心逻辑开发 | v0.2 | P2 |
| 复杂 RAG 检索 | 先不做知识检索，专注流程 | v0.2 | P1 |
| 自动 Skill 沉淀 | Knowledge Evolution 机制后期验证 | v0.3 | P2 |
| 多人协作 | 单用户 MVP 足够展示核心价值 | 长期 | P3 |
| 企业权限管理 | 产品定位不是企业级 | 长期 | P3 |

### 1.2 Agent 层

| 功能 | 推迟原因 | 目标版本 | 优先级 |
|------|---------|----------|--------|
| Research Agent 真实网络搜索 | 需要爬虫/搜索 API 集成 | v0.2 | P2 |
| Agent 自动调用外部工具 | MCP 协议需要完整设计 | v0.3 | P2 |
| Agent 自动并行执行 | 先做串行流程验证逻辑 | v0.2 | P2 |
| 复杂任务依赖图 | 先做简单线性流程 | v0.2 | P2 |
| Agent 自主选择工具 | 先做固定工具分配 | v0.3 | P3 |

### 1.3 Memory 自进化层

| 功能 | 推迟原因 | 目标版本 | 优先级 |
|------|---------|----------|--------|
| 自动写入长期 Memory | 需要设计防污染机制 | v0.2 | P1 |
| Memory 置信度评分 | 评分算法需要验证 | v0.3 | P2 |
| Memory 过期机制 | 过期策略需要设计 | v0.3 | P3 |
| Skill Library 自动生成 | Skill 质量控制复杂 | v0.2 | P1 |
| RAG 检索增强 | 需要向量数据库集成 | v0.2 | P1 |
| Memory 来源追溯 | 需要完整的审计系统 | v0.3 | P2 |

### 1.4 部署与运维层

| 功能 | 推迟原因 | 目标版本 | 优先级 |
|------|---------|----------|--------|
| 多端同步 | 本地先跑通核心流程 | 长期 | P3 |
| Docker 一键部署 | 开发阶段不需要 | v1.0 | P2 |
| 用户登录系统 | 本地单用户足够 | 长期 | P3 |
| 数据加密 | 本地数据暂不需要 | 长期 | P3 |

## 七、功能请求入库标准 📥

**新功能要进入路线图，需要满足以下条件：**

1. **与核心定位一致**：是否符合「多模型 Agent 协作工作台」的定位？
2. **有明确用户场景**：谁在什么情况下需要这个功能？
3. **MVP 已经验证了核心价值**：现有功能跑通了吗？
4. **不破坏现有架构**：可以增量实现吗？
5. **有明确的验收标准**：怎么判断做成功了？

**功能请求模板：**

```
功能名称：
用户场景：
为什么现在需要：
不做的影响：
建议实现方案：
验收标准：
```


## 九、最后原则 🎯

**所有版本迭代都遵循这个优先级排序：**

1. **先稳后快** → 先把现有功能做稳定，再加新功能
2. **先实后虚** → 先做真实能力，再做可视化增强
3. **先核后围** → 先完善核心流程，再加周边功能
4. **先验后扩** → 先验证一个方向可行，再扩大范围
