# ModelGate Agent Studio 下一阶段产品与开发总方案

> 制定日期：2026-07-14  
> 文档性质：下一阶段的产品决策、信息架构、开发范围和验收标准。  
> 当前基线：Runtime、Provider、Supervisor、Memory / Skill、MCP Tool、Dashboard 已具备 MVP 实现；截至本轮实施，后端 217 项测试、前端 153 项测试和生产构建均已通过。  
> 本文优先级高于旧的模块化页面规划。发生冲突时，以本文为准。

---

## 1. 本阶段的核心判断

项目已经有足够多的模块，下一步不应继续以“增加页面 / 增加功能”为主线，而应把已有能力组织成一个可信、连续、可解释的工作流。

产品应从：

```text
多个 Agent 管理功能的集合
```

收敛为：

```text
面向长期开发任务的 AI 团队控制台
让任务在模型之间可解释地路由、执行、交接、审查与复盘。
```

本阶段的第一成功标准不是接入更多模型或工具，而是用户能在一次真实 Goal 中清楚回答：

1. 系统正在完成什么目标？
2. 当前任务由谁、用哪个模型、为什么这样安排？
3. 任务为什么停住、失败或需要交接？
4. 交接后新 Agent 从何处继续，是否真的完成了？
5. 这次运行比“固定使用一个模型”带来了什么收益？

## 2. 已确认的产品决策

### 2.1 Workspace 是主产品，不是附属页面

`Workspace` 是用户执行和理解一个 Goal 的唯一主入口。新建 Goal、查看任务流、触发执行、人工介入、查看路由依据、处理 Handoff、查看最终产物，都应在此完成。

`Dashboard` 只承担全局概况和“进入某个 Goal”的入口职责；不应和 Workspace 重复展示运行细节。

### 2.2 Handoff 不是独立业务页面

Handoff 是一个 **Task 的状态变化和恢复动作**，不是用户需要单独管理的一类工作。

因此：

- 从顶层导航移除 `Handoff Manager` 和 `/handoffs` 的日常入口。
- 不再以“创建演示任务 → 演示交接”作为用户流程。
- 从 Task Card 的异常、额度预警和人工操作中触发 Handoff。
- 在 Task Detail 的 `Handoff` 标签、Workspace 的运行时间线和底部 Console 中展示交接状态、摘要、接手人和结果。
- 原 `/handoffs` 页面在本阶段降级为内部调试 / 历史审计入口；不删除后端接口和数据模型，以避免破坏已有测试与追溯能力。

### 2.3 优先可解释，再提高自动化程度

Planner、Router、Quota、Handoff、Memory 写入都必须展示“做了什么、为什么这样做、用户可否覆盖”。系统不能只显示一个结果。

### 2.4 自进化采取“草稿 + 审核”

Memory Draft 和 Skill Draft 不应直接成为长期知识。只有 Supervisor Review 通过、且用户确认或符合明确的自动批准规则后，才可进入可检索知识库。

### 2.5 工具能力以安全与审计优先

MCP 的价值不在于工具数量，而在于每一次调用都能说明：哪个 Goal、哪个 Task、哪个 Agent、什么授权、调用了什么、产生了什么影响。

## 3. 目标体验：一条完整的 Goal 工作流

```text
Dashboard
  └─ 进入 / 创建 Goal
       └─ Workspace
            ├─ 明确 Goal、约束、完成标准与运行配置
            ├─ Planner 生成任务计划，用户可确认或修改
            ├─ Router 为每个 Task 给出模型选择和理由
            ├─ Runtime 执行，界面持续呈现状态、输出、日志、成本与风险
            ├─ 异常时在当前 Task 内提出 Retry / Override / Handoff / Stop
            ├─ Handoff 生成摘要，用户查看并确认接手方案
            ├─ 新 Worker 继承上下文继续执行
            ├─ Supervisor 给出最终结果、质量审查与风险说明
            └─ Evolution Review 审核可沉淀的 Memory / Skill 草稿
```

### 3.1 Handoff 的标准交互

| 阶段 | 用户看到什么 | 用户可以做什么 |
|---|---|---|
| 预警 | Task Card 显示额度、错误或质量风险，以及原因 | 查看详情、继续尝试、改模型、交接、暂停 |
| 决策 | Handoff Sheet 展示来源 Agent、候选接手 Agent、理由、预计影响 | 选择接手 Agent / 模型，补充要求，确认或取消 |
| 摘要 | 结构化摘要：已完成、未完成、约束、关键决定、风险、下一步、必要上下文 | 审阅、复制、返回修改交接配置 |
| 接手 | 同一张 Task Card 显示“由 A 交给 B”，Worker 与模型切换 | 查看交接前后差异、停止或重试 |
| 结果 | Task 完成 / 失败，并保留 Handoff Timeline | 展开审计记录、从历史中复盘 |

**界面承载规则：**

- 快速操作：Task Card 的状态操作区。
- 决策与确认：右侧 `Task Detail Panel` 或一个不离开 Workspace 的侧滑 Sheet。
- 历史与时间线：Task Detail 的 `Handoff` Tab 和 Bottom Console 的过滤视图。
- 全局审计：仅在 Logs 中按事件筛选；不再使用独立产品页。

## 4. 新的信息架构

### 4.1 顶层导航（目标态）

```text
Dashboard | Workspace | Agents | Models | Tools | Evolution | Logs | Settings
```

说明：

- `Workspace`：默认执行入口，承载 Goal、Task、Router、Quota、Handoff、最终输出。
- `Agents / Models / Tools`：配置层，通常在执行前或排障时访问。
- `Evolution`：审核 Memory / Skill 草稿，不与运行时工作区混杂。
- `Logs`：全局审计 / 排障层；Handoff 作为可筛选事件存在。
- `Quota`、`Model Router`：从独立顶层页面降为 Workspace 上下文能力；可保留内部配置路由，但不作为主导航。

### 4.2 Workspace 的目标布局

```text
┌───────────────────────────────────────────────────────────────────────┐
│ Goal Header：目标、状态、进度、成本、时长、风险、暂停/继续             │
├───────────────┬───────────────────────────────────┬───────────────────┤
│ Plan / Tasks  │ Collaboration Flow                │ Context Inspector │
│               │                                   │                   │
│ Goal brief    │ 当前任务流 + Agent 工位           │ Task              │
│ Task tree     │ 每卡：负责人、模型、路由理由      │ Router            │
│ Run config    │ 输出片段、状态、风险、操作        │ Handoff           │
│               │                                   │ Context / Logs    │
├───────────────┴───────────────────────────────────┴───────────────────┤
│ Console：事件 · 调用 · Token/成本 · Handoff · 错误（默认摘要）         │
└───────────────────────────────────────────────────────────────────────┘
```

### 4.3 视觉与交互原则

1. 中央区域先表达“任务如何推进”，而不是拆成 Task 区和 Agent 区两组静态卡片。
2. 状态色只表达状态；不要用渐变、持续装饰动画或过多颜色制造 AI 感。
3. 动效只用于告知状态变化：开始执行、阻塞、交接、完成、出错。
4. 详情面板遵循渐进披露：默认展示当前决策与下一步，完整日志、Prompt、上下文按需展开。
5. 用户可随时停止、重跑、替换模型、触发交接或查看原因；这些都是“人控制 AI 团队”的关键。

## 5. 分阶段开发计划

### Phase A：Workspace 重构与 Handoff 收拢（P0）

**目标：** 让界面与真正的产品主线一致，不离开 Workspace 即可完成一条交接。

#### 实施进度（2026-07-14）

| 项目 | 状态 | 说明 |
|---|---|---|
| Handoff 从日常顶层导航移除 | 已完成 | 保留 `/handoffs` 路由作为兼容 / 内部审计入口。 |
| Workspace Task 发起与查看 Handoff | 已完成 | Task Card、Task Detail 与 Handoff Sheet 已连通。 |
| 正常 Workspace Task 的后端交接 | 已完成 | Handoff Service 同时支持 Runtime 的 `Task` 与旧 `HandoffTask`。 |
| Workspace 聚合交接时间线 | 已完成 | `/workspace/{goal_id}/state` 返回 Goal 下的 `handoffs`，并附在每个 Task。 |
| 首次启动可执行性 | 已完成 | Agent Station 为空时写入默认角色 Agent；无 Planner 的部署会阻止 Goal 创建并返回明确错误。 |
| 任务协作流视觉重构 | 已完成首轮 | 中心区改为带步骤编号的串行协作流；新 Goal 会生成 `Planner → Coder → Reviewer` 的可执行计划。任意 DAG/依赖图仍属于后续 Runtime 能力，界面不再伪造并行。 |
| Router / Context / Logs 详情标签 | 已完成首轮 | 由 Workspace 聚合数据提供：最新路由决策、当前 Worker 上下文和最近 10 条 Task 日志。 |

#### 前端任务

1. 移除顶层导航中的 `Handoff Manager`、`Quota Manager`、`Model Router`。
2. 重构 `WorkspacePage`：中心区改为任务协作流，避免当前“Task 网格 + Agent 网格”重复表达。
3. 扩展 `TaskCard`：显示当前 Agent、模型、路由简述、额度 / 错误风险、最新输出和上下文操作。
4. 完成 `TaskDetailPanel` 的 `Router`、`Handoff`、`Context`、`Logs` 标签；不再保留占位内容。
5. 把现有 `HandoffConfirmModal`、`HandoffDetailDrawer` 迁入 Workspace，由选中 Task 驱动。
6. Bottom Console 支持按当前 Task 自动过滤，并增加 Handoff 事件标签。
7. `HandoffPage` 从主路由移除；保留为非导航的 internal/audit 页面，或后续并入 Logs。

#### 后端 / API 任务

1. Workspace state 返回当前 Task 的 `routing_decision`、`quota_status`、最新 `handoff` 摘要字段。
2. 提供按 Task 查询 Handoff Timeline 的聚合接口，避免前端拼接多次全局查询。
3. Handoff accept 成功后自动刷新 Workspace State，并把新 Worker、模型和交接来源写入日志。
4. 不更改已有 Handoff 数据表和核心 API 的语义；新增聚合 DTO 保持向后兼容。

#### 验收标准

- 用户不访问 `/handoffs`，也能从一个运行中的 Task 完整完成“触发 → 选择接手人 → 阅读摘要 → 接手 → 继续执行 → 查看结果”。
- Workspace 任何时刻都能看出：当前执行者、所用模型、任务状态、风险和下一步操作。
- Handoff 的完整事件可在当前 Task 详情及 Logs 追溯。

### Phase B：可信执行闭环与可解释路由（P0）

**目标：** 把 Runtime 由“能跑”提升为稳定、可重复演示的真实链路。

#### 实施进度（2026-07-14）

| 项目 | 状态 | 说明 |
|---|---|---|
| 串行 Goal 生命周期 | 已完成首轮 | 完整角色配置下创建 `Plan → Build → Review`，并由 Runtime 串行执行；取消、任意 DAG 仍待后续能力。 |
| 路由决策与切换可解释性 | 已完成首轮 | Task 详情显示候选/备选、原因、风险、额度、Context 与日志；Handoff 后复用确认模型。 |
| 最终运行报告 | 已完成首轮 | 完成后展示已完成/未完成、质量检查、风险、模型、Token、Handoff；没有 Provider 单价表时明确标记货币成本不可用。 |
| 三条可重复 Demo / 浏览器 E2E | 进行中 | 后端已覆盖正常、额度交接、Provider 失败续跑；Workspace 浏览器流程已人工验证，待固化为独立可重复脚本。 |

1. 统一 Goal 运行生命周期：计划确认、执行、等待人工决策、交接、审查、完成、失败、取消。
2. 每个 Task 保存并展示路由决策：候选模型、淘汰原因、最终选择、成本 / 速度 / 上下文 / 额度评分。
3. 提供固定 Demo Goal 与可重复 E2E 脚本，至少覆盖：正常完成、额度预警交接、Provider 失败后切换模型。
4. Supervisor Final Summary 必须包括：完成内容、未完成内容、质量结论、风险、使用模型、成本与交接次数。
5. 增加运行指标：耗时、token、估算成本、失败重试、Handoff 次数、人工干预次数。

#### 验收标准

- 三条 Demo 路径稳定通过，且从 Workspace 可完整观察每一步。
- 用户能理解“为什么是这个模型”，并能手动覆盖决定。
- 最终报告能说明结果质量与运行代价，不只是拼接输出。

## 6. 暂不做的事项

本阶段明确不做：

- 并行多 Agent 调度、复杂 DAG 自动优化；先稳定串行 + 简单依赖。
- 多人协作、组织权限、Agent / Skill 市场。
- 像素办公室作为主视图；它可作为后续可选观察模式，不能替代协作流可读性。
- 接入大量 Provider；优先把一个 OpenAI-compatible Provider 和 Mock 路径做稳。
- 未审核的长期 Memory / Skill 自动写入。
- 为展示而存在的独立 Handoff 管理业务页面。

## 10. 最终验收问题

本阶段完成时，必须能够对以下问题回答“是”：

1. 新用户是否只进入 Workspace 就能理解并操控一个 Goal？
2. Handoff 是否自然地表现为 Task 的连续执行，而不是跳去另一个管理系统？
3. 用户是否能理解每次路由、切换和交接的原因，并手动覆盖？
4. 用户是否能同时看到质量、成本、速度和风险，而不只看到模型输出？
