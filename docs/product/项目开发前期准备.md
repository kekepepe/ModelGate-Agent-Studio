从专业 AI 产品经理角度看，你**现在已经有了产品定义、核心模块、MVP 范围、数据对象、架构差异化**这些大方向文档。现有文档已经明确了：不是万能 Agent，而是先做“清晰可控的多模型 Agent 协作工作台”；MVP 必须包含多模型接入、Agent 配置、Goal 输入、任务拆解、状态记录、Handoff Summary、基础工位可视化和最终结果汇总；同时也明确了自动读取所有 coding plan 真实额度、完整像素办公室、高级工具调用等可以暂缓。

所以我不建议继续写很多“宏大叙事文档”。真正开始 vibe coding 前，最需要补的是 **能直接指导代码落地的执行型文档** 。

## 一、现在最应该补的文档

### 1. v1 MVP 冻结文档

这是最重要的。它要把“第一版到底做什么、不做什么”彻底锁死。

建议 v1 只做：

```text
用户输入 Goal
→ 系统拆成 3 个以上 Task
→ 分配给 Planner / Coder / Reviewer / Summarizer / Supervisor
→ 每个 Agent 有状态
→ 工作区展示卡片流转
→ 可以生成 Handoff Summary
→ 可以保存执行日志
→ 最后生成汇总结果
```

v1 暂时不要做：

```text
真实复杂自动代码修改
完整 MCP 插件生态
真实读取 Claude Code / Codex 额度
完整像素办公室动画
复杂 RAG
自动 Skill 沉淀
多人协作
企业权限
```

你的文档里已经写过“当前阶段不追求完全自动化开发大型项目、复杂插件生态、企业级权限、大规模团队协作”，这个判断是对的。vibe coding 最怕一边写一边加范围，最后变成半成品集合。

---

### 2. 核心用户流程文档

不是普通流程图，而是要写成“用户点哪里、系统发生什么、页面怎么变”。

至少写 3 条：

**流程 A：创建 Goal**

```text
用户输入目标
→ Router 判断任务类型
→ Planner 拆解任务
→ 生成任务卡片
→ 卡片进入 Workspace
→ Agent 状态从 idle 变为 working
```

**流程 B：Agent 执行任务**

```text
任务分配给 Agent
→ Agent 读取任务上下文
→ 调用模型
→ 生成中间输出
→ 更新 Task 状态
→ 写入日志
```

**流程 C：Handoff 交接**

```text
Agent 无法继续 / 模拟额度不足 / 用户手动触发
→ 系统生成 Handoff Summary
→ 选择接手 Agent
→ 新 Agent 读取摘要
→ 继续任务
→ Handoff 页面记录交接历史
```

你现有文档已经定义了标准任务流程、额度不足交接流程、问题路由流程，这部分可以直接整理成“开发用流程说明”。

---

### 3. 页面 PRD / 页面功能说明

你现在需要把页面结构变成每个页面的功能清单。

至少需要这几个页面：

```text
1. Dashboard
2. Workspace
3. Agent Registry
4. Models
5. Quota
6. Handoff
7. Logs
8. Knowledge Base / Skill Library 后期再做
```

其中 v0.1 最核心的是  **Workspace** 。

Workspace 要单独写清楚：

```text
左侧：Goal 输入区
中间：卡片任务流视图 / 像素办公室视图
右侧：任务详情
底部：执行日志
顶部：模型额度状态 / 当前运行状态
```

你之前说的两个视图也要写进去：

```text
默认进入：卡片网格 + 任务流视图
可切换：像素办公室视图
切换时：允许有 loading / rendering 状态
卡片视图负责清晰表达任务逻辑
像素视图负责增强可视化体验
```

这里要明确一点：**v0.1 应该先把卡片任务流做扎实，像素办公室作为可切换展示层，不要让像素动画拖慢核心逻辑开发。**

### 4. 数据结构 / 数据库 Schema 文档

这个必须补。因为你的产品本质不是聊天界面，而是“Goal / Task / Agent / Worker / Handoff / Memory / Log”的状态系统。

最少需要这些表或对象：

```text
Model
AgentStation
WorkerSession
Goal
Task
HandoffRecord
ExecutionLog
Provider
QuotaUsage
MemoryItem 后期
Skill 后期
```

你现有文档已经列了 Model、AgentStation、WorkerSession、Goal、Task、HandoffRecord 的字段，这部分可以继续扩成数据库 schema。

建议你在 vibe coding 前把每个对象写成这种格式：

```text
Task {
  id
  goal_id
  parent_task_id
  title
  description
  assigned_agent_id
  status: pending | running | waiting | handoff | completed | failed
  priority
  dependencies
  output
  completion_criteria
  created_at
  updated_at
}
```

尤其要先确认所有状态枚举，不然后面前端状态灯、卡片颜色、日志、Handoff 都会乱。

### 5. Agent Runtime 规则文档

这个是你项目的“内核说明书”。

要写清楚每个 Agent 执行任务时的标准流程：

```text
接收 Task
→ 加载 Agent Profile
→ 加载相关 Memory / Context
→ 选择模型
→ 组装 Prompt
→ 调用模型
→ 保存输出
→ 判断是否完成
→ 判断是否需要 Handoff
→ 进入 Supervisor 审查
```

你已有架构文档里已经定义 Runtime 需要记录 task_id、agent_id、model_id、prompt、retrieved_memory、tool_calls、intermediate_outputs、errors、token_usage、quota_status、handoff_status、final_output。这个应该直接变成开发字段和日志字段。

v0.1 可以先做“伪 Runtime”：

```text
不真正自动跑复杂 Agent
先用后端服务模拟 Agent 执行流程
每一步有状态变化、日志、输出
之后再接真实模型调用
```

这样更稳。

### 6. Prompt 模板文档

你的 Agent 平台不是只有 UI，核心还包括每个 Agent 的 prompt 行为。

至少要写：

```text
Router Agent Prompt
Planner Agent Prompt
Coder Agent Prompt
Reviewer Agent Prompt
Summarizer Agent Prompt
Supervisor Agent Prompt
Handoff Summary Prompt
Knowledge Evolution Agent Prompt 后期
```

每个 Prompt 要定义：

```text
是否允许触发 Handoff
```

例如 Handoff Summary 的输出必须结构化：


你的产品文档已经把 Handoff Summary 的内容定义得比较清楚，接下来要把它变成固定 JSON 或 Markdown 模板。

### 8. UI 状态与交互动效文档

这个文档不是视觉稿，而是状态规则。

例如 Agent 卡片状态：

```text
idle：灰色，空闲
planning：蓝色，正在规划
working：蓝色 / 动态点，工作中
waiting：黄色，等待依赖
handoff：紫色，交接中
completed：绿色，完成
failed：红色，失败
```

你现有文档已经有状态灯设计：灰色空闲、蓝色工作中、黄色等待或额度不足、红色出错、绿色完成、紫色交接中。这个应该直接作为前端状态系统。

还要确认：

```text
任务卡片什么时候缩略？
任务完成后是否自动折叠？
新 Agent 出现时卡片怎么生成？
卡片之间连线代表依赖，还是执行流？
连线颜色代表状态，还是任务类型？
像素视图是否和卡片视图共享同一套状态数据？
切换视图时是否保留当前任务焦点？
```

我的建议是：**两个视图必须共享同一套底层状态数据，只是渲染方式不同。**
否则后期会变成两个系统，维护成本很高。

### 9. Memory / Skill v0.1 简化文档

你已经规划了 Raw Memory、Session Memory、Project Memory、User Memory、Agent Memory、Skill Memory，这个方向没问题。

但 v0.1 不要全部做。先写一个简化版：

```text
v0.1 只做：
- Execution Log

- Project Memory 草稿

v0.2 再做：

v0.3 再做：
```

这里必须确认一个核心原则：

因为你这个项目如果 Memory 污染，后面 Agent 会越来越不稳定。

## 二、开始前必须确认的关键细节

### 1. 这个项目到底是独立做，还是嵌进 ModelGate？

我的建议：**先独立做。**

原因：

```text
1. 不会被 ModelGate 原有前端结构限制
2. 可以重新设计 Workspace 体验
3. 更适合作为实习作品单独展示
4. 后期再把 ModelGate 的多模型能力迁移进来
5. 避免一开始陷入旧项目适配和重构
```

你现在可以把它理解成：

```text
ModelGate Agent Studio = 新项目
ModelGate 原项目 = 未来可复用的 Provider / Model Router / API Key 管理基础
```

---

### 2. v0.1 是“真实 Agent 执行”还是“可视化模拟 + 部分真实调用”？

建议选后者。

也就是：

```text
前端真实
状态真实
任务拆解可以真实调用模型
Agent 执行可以先半模拟
Handoff Summary 可以真实生成
额度不足可以先手动触发 / 模拟触发
```

不要一上来追求完全自动开发项目。你现有架构也明确当前阶段不追求完全自动化开发大型项目和完全无人监督。

---

### 3. 第一版支持哪些模型？

建议 v0.1 只支持：

```text
OpenAI-compatible API
Anthropic
DeepSeek
Kimi / Moonshot
本地 mock model
```

先不要把所有 provider 都接进去。
你需要的是证明“多模型 Agent 调度逻辑”，不是证明“我接了很多 API”。

---

### 4. Quota Manager 第一版怎么做？

真实读取 Claude Code / Codex 的 plan 额度很难。

所以 v0.1 建议：

```text
API 模型：记录 token / 请求次数
Coding Plan：手动配置每日/每窗口额度
Mock Quota：人为设置“接近额度不足”
Handoff：先支持手动触发 + 规则触发
```

比如：

```text
当某模型本轮调用次数 >= 用户设置上限 80%
→ 标记为 warning
→ 可以触发 Handoff
```

这比硬做真实额度读取更现实。

---

### 5. Agent 和 Model 的关系必须确认

你现在的设计是对的：

```text
Model 不是 Agent。
Agent = 职责 + 模型 + 工具权限 + 上下文 + 当前状态。
```

这点必须写进开发规范。否则前端和后端会把 Claude、GPT、Kimi 直接当成 Agent，产品逻辑就会退化成“多模型聊天工具”。

---

### 6. Workspace 两种视图的底层关系

建议确认成：

```text
卡片视图 = 默认主视图
像素办公室 = 可切换展示视图
两者共用同一套 Goal / Task / Agent / Worker / Handoff 数据
卡片视图优先保证清晰
像素视图优先保证体验
```

技术上不要写两套业务逻辑，只写两套 renderer。

---

### 7. 是否允许 Agent 自动修改本地代码？

v0.1 建议：**不默认允许。**

可以做成：

```text
v0.1：生成修改建议 / patch 文本 / 文件计划
v0.2：用户确认后写入文件
v0.3：接入 MCP / 本地文件系统 / GitHub PR
```

因为一旦允许自动改文件，就必须做权限、安全、回滚、diff、审批。你的架构文档里也已经强调 MCP 需要 Tool Permission Policy、Tool Call Logs、Tool Approval Flow、Tool Sandbox。

---

## 四、最终判断

你现在不是缺“产品想法”，而是缺 **开发冻结层** 。

也就是说，目前已经知道：

```text
这个产品是什么
为什么有差异化
大概有哪些模块
长期愿景是什么
```

但 vibe coding 前还必须确认：

```text
第一版到底做哪些页面
哪些按钮能点
哪些状态会变
哪些数据要存
哪些接口要有
Agent 怎么跑
Handoff 怎么生成
Memory 第一版做到哪一步
Demo 怎么展示
```

我的建议是：**先补 8 份轻量开发文档，每份不用长，但必须能直接变成代码任务。**
写完这些再 vibe coding，项目会稳很多；不写的话，大概率会先做出一个好看的前端壳，但 Agent Runtime、状态流转、Handoff、Memory 会很快混乱。
